# 设计说明

这份文档写给想看懂它为什么这么做的人：同行、面试官、以及半年后忘了自己当初在想什么的我自己。

它不讲怎么用（那是 [`GUIDE.md`](GUIDE.md)），只讲取舍：**为什么是这个形状，代价是什么。**

---

## 一句话架构

一个 1 万行的 HTML 文件，内联 CSS + 内联 JS，零依赖，数据在 `localStorage`。

```
Sea-2.8.html
├─ <style>    设计系统：CSS 变量 + 八个页面的布局
├─ <body>     八个页面的静态骨架（JS 只改内容，不建骨架）
└─ <script>
   ├─ 数据层    卡片 / 航线 / 流水 → 一个 JSON → persist()
   ├─ 存储层    localStorage（真源）→ 启动快照 → 可选文件镜像 → 可选云端
   ├─ 渲染层    refreshAllViews() 按页面分发到各 render*()
   └─ 交互层    拖拽 / 右键菜单 / 弹窗（草稿态，保存才提交）
```

渲染是「一份数据 + 全量重画」，没有虚拟 DOM、没有响应式框架、没有状态机。八个页面在数据变动后主动 `refreshAllViews()`。

## 为什么是单文件

这不是「还没拆」，是产品形态本身：

| 想要 | 单文件给的 | 拆成工程给的 |
|---|---|---|
| 发给别人一个东西就能用 | 一个 `.html` | 一个仓库 + 一次构建 |
| 十年后还能打开 | 只依赖浏览器 | 依赖当时的工具链 |
| 断网、公用机、U 盘能跑 | 直接双击 | 需要 node / 服务器 |
| 改动的影响面可推理 | 靠纪律 + 代码地图 | 靠模块边界 + 类型系统 |

代价我认：**没有模块系统，改动的影响面靠纪律而不是编译器。** 所以这个项目把工程精力花在了三件事上——三个版本的白名单导出、可重复运行的回归脚本、以及 `docs/audit/AUDIT-01-代码地图.md`（一万行里这一行归谁）。

用 Vue / React 重写一遍会让代码更漂亮，但会输掉上面那张表的第一、二、三行。**不做。**

## 数据模型

三种卡，按「有没有终点」分，而不是按领域分：

| 层 | 特征 | 例子 |
|---|---|---|
| **讨伐** | 有死线 | 考完六级、投完一轮简历 |
| **修行** | 没有终点，只有频率 | 每周三次训练 |
| **铸造** | 有明确产出物 | 一份简历、一个作品 |

领域（海域）是**卡上的标签**，不是装卡的盒子——同一张健身卡可以挂在「健康」上，也可以挂在「成长」的目标下，统计口径以「有没有部位标记 / 属不属于该海域」取并集（这条踩过坑：热力图和本周训练曾经各算一套）。

状态是两层，这一条是整个设计里最贵的决定：

- **计划层**（`ROUTE` 航线）可以被改：改一次，从今天起生效。
- **事实层**（`occMoves` / `occGone` / `occDone` 三张表）只追加：单独挪一天、单独删一天、单独打一个勾，都记在这里。

## 派生卡为什么不能写回源

航线（专线 / 环线）会把卡「铺」到日历上，铺出来的那张是**派生卡**。它在界面上和一次性卡长得完全一样，可以单独拖、单独删、单独打勾。

它**不回写航线**，状态全部记在三张实例表里，键是 `rtId|原生日期|原生格`。

原因是一次真实的需求冲突：如果一次拖动就改了航线，那「这周临时挪一下」会变成「以后每周都挪」——用户想改一天，结果改了整年。反过来，如果派生卡不能单独动，那它就是个摆设。

于是拆成两层：**航线是模板，派生卡是当次实例，模板不因实例而变。** 代价是多三张表和一套键的拼接逻辑，以及「编辑航线后已有实例怎么算」这种必须逐个想清楚的问题。

相关的事故与改动记在 `CHANGELOG.md` 里关于派生卡的那几条。

## 环线只作用被排入的那一周

环线卡可以按星期重复（每周一三五），但它只影响**你把它拖进去的那一周**（记 `weekAnchor`，即那周的周一）。下一周不会自动继续。

这是刻意的：自动无限重复会让日历变成一堆你从没同意过的条目，而「这周想做」和「以后一直做」是两种意图，不该用同一个动作表达。

代价是每周要重拖一次。是否加「排一次、长期生效」的开关，还挂在待办里，没定。

## 存储：四层，一个真源

```
localStorage.sea_workspace_v1   ← 唯一真源（约 10KB）
        │
        ├─ 启动前快照     sea_snap_main / sea_snap_assets / sea_snap_at
        ├─ 文件镜像（可选）用户绑定的 sea-存档.json，句柄存 IndexedDB
        └─ 云端（可选）  一条主记录 slot=master + 附件 4 片 assets0..3
```

**关键约束：文件是副本，不是主人。**

绑定存档文件之后，每次改动会整份重写那个文件；只有当**文件比本机新**（比 `savedAt`）时才会自动载入它。所以你在外面手改它、网盘把它回滚成旧版，都不会让你丢数据。

如果反过来让文件当真源，就必须处理「两边都改了怎么办」——那是同步问题，会引入冲突仲裁、合并策略、版本向量。而这个产品连账号都没有。**不做，是设计。**

云端同理：只在支持 `window.__SMART_PAGE__` 的宿主里启用，公开版默认不可用。附件按 4 片切分，装不下的会明确提示「只存在本机」而不是静默丢弃。

## 已经踩过的坑（都留了底）

这几条写在这里，是因为它们看起来像小问题，实际都是会让人放弃这个工具的那类问题：

1. **「只改内存不落盘」的入口。** 早期拖拽排期只改内存、靠定时器兜底，中途刷新就丢。后来逐个出口补了 `save()`。
2. **`getDay()` 周日是 0。** 环线按星期匹配时用过 `getDay()+1`，于是周一被渲染成周二。渲染、拖拽高亮、清空判定三处必须同一个映射。
3. **日历被侧栏挤窄。** 侧栏用百分比宽度，屏幕一变日历就被压到看不清；改成固定像素宽才根治。这条教训写进了 UI 规格：**能挤压主内容的侧栏，宽度必须固定。**
4. **拖航线时格子弹动效。** 落点本身就是语义，加动效反而让人以为没拖对。
5. **窄栏里塞图表。** 两个图各分到 5px 宽，视觉上就是「图表消失了」。规则改成：计数可以塞窄栏，图表必须有宽度。

## 工程纪律：没有编译器的项目怎么保命

1. **一套代码，三个形态。** 源文件 / GitHub 发布版 / 线上部署件。同步只有一个方向：源 → 发布版 → 线上，发布版和线上永不反向流回源。
2. **发布版是白名单导出的产物**，不是手改出来的。`scripts/export-public.mjs` 按 `git ls-files` 复制，`scripts/sync-check.mjs` 只读校验三者是否对齐。
3. **回归脚本可重复运行。** `npm test` 一条命令跑完空白首启、数据口径、存档文件、XSS 载荷四项；`npm run test:visual` 做像素级外观回归。
4. **每次改动先备份再动。** 历史版本永不删除——那是这个项目最贵的资产。
5. **事故必须写根因。** `CHANGELOG.md` 里每条事故都记了「为什么会发生」，比记「改了什么」有用得多。

## 技术债（明确记着，不是不知道）

- `persist()` 每次全量 `JSON.stringify`。无附件时约 0.2ms，带 base64 附件时 10–30ms。改法是脏标记 + 定期兜底，但要连带改存档层，一直没找到值得单独做的时机。
- **附件存在 `localStorage` 里（配额约 5MB）**，而不是 IndexedDB（可用到 GB 级）。这是下一个该做的结构改动。
- 拖拽、右键菜单这些交互路径**没有自动化测试**，靠人工点检。jsdom 测不出布局，也测不出 `beforeunload → reload` 的竞态，所以这一层只能用真浏览器，成本高。
- 没有类型系统。一万行的字段拼写错误只能靠跑起来才能发现。

## 怎么读这份代码

建议顺序（括号里是它在文件里的大致位置）：

1. `<style>` 顶部的 `:root` CSS 变量——设计系统的全部颜色和圆角。
2. `persist()` / `loadStore()`——先搞清数据怎么进怎么出。
3. `refreshAllViews()`——它列出所有渲染入口，等于一份目录。
4. `renderCalendar()` / `renderRouteSlots()` / `renderIslandPool()` / `renderSailPool()`——最复杂的一组：周历 + 三个卡池 + 航线派生。
5. 剩下的按页面顺着看（`renderCareer*` / `renderFin*` / `renderHlth*` / `renderTide`）。

更细的模块地图和函数归属在 [`audit/AUDIT-01-代码地图.md`](audit/AUDIT-01-代码地图.md)；已知缺陷与风险分级在 [`audit/AUDIT-03-缺陷与风险清单.md`](audit/AUDIT-03-缺陷与风险清单.md)。
